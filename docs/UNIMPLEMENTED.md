# Register of unimplemented and hardware-dependent features

Required by the specification: *"Record any feature that cannot be verified or
implemented without hardware"* and *"a clear list of unimplemented or
hardware-dependent features."*

This register is the single place that answers "does the system do X?" honestly.
If a feature is not listed here and not described in a themed document, treat it as
not implemented.

**Reporting convention, used throughout:** ✅ done · ⚠️ partial · ❌ not done ·
🔌 blocked on hardware or a commercial agreement · 📄 documented but unverified.

---

## 1. 🔌 Blocked on hardware

These cannot be completed, or honestly claimed, without physical equipment. Nothing
here has been tested.

| Feature | Why it is blocked | What is needed to close it |
|---|---|---|
| **End-to-end GPS tracker verification on H02:5013** | No tracker has ever connected. The port listens; no device has spoken to it. | One SinoTrack ST-906L (or equivalent), a SIM, and `docs/TESTING.md` |
| **Tracker protocol confirmation** | The device's actual protocol is assumed from documentation, not observed. It may need GT06, or a different port entirely. | The device, and its traffic |
| **Overspeed, power-disconnect (tamper) and SOS notifications** | Each depends on the specific device emitting the event. Traccar supports them; **the tracker is unverified**, and it is wrong to claim them first. | The device, then deliberately trigger each condition |
| **Ignition/ACC detection** | A wired input. Cannot be simulated from documentation. | Installation and a wiring check |
| **Geofence accuracy in the field** | Geofence *mechanics* are Traccar's and are mature; zone boundaries against real GPS drift are not tested. | The device, driving a known route |
| **Ignition-gated reporting / SMS configuration** | Device-specific SMS command sets, and a wrong one can brick the unit. | The device, plus its manual |
| **Battery and solar variants (cargo/pallet trackers)** | Deployment-specific hardware. | Purchase decision not taken |

## 3. ❌ Not implemented — tachograph

| Feature | Status | Note |
|---|---|---|
| **Vehicle-unit (VU) download parsing** | ❌ **REFUSED BY DESIGN** | A VU download is a stored SID/TREP response stream, not a TLV container, and the per-TREP body layouts could not be verified. The parser detects a VU file and refuses it rather than producing confidently wrong driving hours. `TREP 06` (a card download embedded in a VU file) **is** decoded |
| GEN2 / GEN2v2 card and VU files | ❌ **NOT IMPLEMENTED** | Refused, for the same reason: GEN2 offsets applied to GEN1 structure produce plausible nonsense |
| Card signature and certificate verification | ❌ **NOT IMPLEMENTED** | The parser **preserves** signature objects (they are visible in `raw_evidence`) but does not validate them. Verification needs the European public key infrastructure. Malformed-file handling does not depend on it |
| External parser adapter against a **real** parser | ❌ **NOT DONE** | The adapter is implemented and **22 tests** drive it with stub commands, covering JSON mapping, malformed payloads, timeouts, non-zero exits, missing binaries and oversized output. **No external binary is installed**, so `tachograph-go` itself has never been invoked |
| Driver-card *events* and *faults* (TREP 03 / card event records) | ❌ **NOT IMPLEMENTED** | Only activity records are normalised |
| Detailed speed (TREP 04) and technical data (TREP 05) | ❌ **NOT IMPLEMENTED** | Not needed for driving time |
| Places / daily work period records | ❌ **NOT IMPLEMENTED** | Arrival and location-from-tachograph is not built |
| Cross-checking tachograph activity against GPS positions | ❌ **NOT IMPLEMENTED** | Would be a strong integrity check (does the card's driving time match the vehicle's movement?) and is an obvious next step |
| Multi-manning (Art 8(5)) as an assessed finding | ⚠️ **PARTIAL** | Co-driver rows are parsed and retained; the 30-hour/9-hour rule is defined as constants but is not emitted as a finding. No mixed-crew file has been tested |
| Weekly-rest compensation actually taken | ❌ **NOT IMPLEMENTED** | The engine flags that compensation is *required*; it does not verify it was taken. Reported as `compensation_verified: false` |
| Working time (Directive 2002/15/EC) | ❌ **NOT IMPLEMENTED** | Out of scope by design and stated on every result |
| Occasional passenger transport (Reg (EU) 2024/1258) | ❌ **NOT IMPLEMENTED** | Out of scope; this is goods transport |
| Automated re-parse when the parser version changes | ⚠️ **MANUAL** | The procedure is documented in `docs/TACHO-SERVICE.md` §7; there is no scheduler |
| Retention/deletion automation for driver data | ❌ **NOT IMPLEMENTED** | Nothing deletes anything automatically. The policy is in `docs/SECURITY.md`; the tooling is not written |

| Backup covering the tachograph volume | ⚠️ **GAP** | `scripts/backup.sh` dumps PostgreSQL only. The `tacho-data` volume holds the uploaded originals and **must be backed up alongside it**, or a restore leaves imports pointing at missing files. Not yet automated |

| Role separation | ⚠️ **PARTIAL** | The tachograph API enforces `owner` / `fleet_manager` / `viewer`. Traccar enforces its own users and permissions. **There is no single sign-on between them**; the dashboard is expected to authenticate against Traccar and forward the identity |
| Audit logging | ⚠️ **PARTIAL** | The tachograph service audits every read and write of driver data with actor, role and source IP. Traccar's own actions are not mirrored into it |

## 7. Known constraints and traps

Recorded so they are not rediscovered expensively.

1. **Traccar creates no users on first boot.** The stack passes every healthcheck and
   nobody can log in. `scripts/create-admin.sh` plus a one-time registration flag is
   the supported path. See the README's *First run*.
2. **A Compose project-name change silently orphans named volumes.** Renaming the
   project gives a fresh empty database and leaves the real one behind. Do not rename
   `gpstracer`.
3. **Traccar's web port is bound to loopback on purpose.** Putting a reverse proxy in
   front is required, not optional, before this is reachable from the internet.
4. **The tachograph database and the `tacho-data` volume must be restored together.**
   See §5.
5. **`tacho_imports` is both a queue and an audit trail.** Truncating it discards
   import history, not just pending work.
6. **Local environment note.** During this work, two unrelated things were found in
   the host's Docker state and left alone deliberately: multiple checkouts of this
   project exist (`~/Desktop/GPS_Tracer`, `~/Desktop/GPS_Tracker`, and the copies
   inside `~/Desktop/gpstracer`), and the container `gpstracer-db-1` is in a
   **crash-loop** (`chown: /var/lib/postgresql/data/mysql.sock: No such file or
   directory` — a MySQL data directory mounted into a `postgres:16-alpine` image).
   It belongs to a different checkout and was not modified. It should be removed or
   repaired, and the ownership of the checkouts settled, before anyone acts on the
   "which directory is the real repository" question.
