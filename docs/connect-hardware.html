How a tracker reaches this server

Six hops between a box under a dashboard and a dot on the fleet map. Every one of them fails silently, and the symptom is nearly the same each time: nothing appears. Work down the numbered hops, not across the map.

01

The path

numbered hops, read left to right

The tracker never receives a connection: it opens one, out of the vehicle's data session, to this server's public port. That single direction is why a car-park of SIMs behind carrier NAT still works, and why nothing on the server needs a route back into the vehicle.

02

What each hop can be wrong about

one cause, one check

Read the symptom column until you recognise what you are seeing, then run the check beside it. Do not change two things at once — with six silent hops that is how an afternoon disappears.

Hop What has to be true How it fails, silently The check
Hop 1SMS provisioning The unit accepts the APN, the server address and the reporting intervals. An unrecognised command is ignored without a reply. The only symptom is that nothing ever arrives. Send RCONF. Expect SET OK, and MODE:GPRS with your APN and server in the reply.
Hop 2Data session The SIM attaches, the APN is right, and roaming is covered for every country the trucks reach. The device has no screen, so a SIM that cannot attach is indistinguishable from dead hardware. Put the SIM in a phone first. Test it before it goes in the unit.
Hop 3TCP 5013 in The published host port lands on 5013 inside the container, where Traccar's H02 listener actually is. Point the host at any other number and it lands on a different Traccar listener — its watch port is 5093. The stack comes up healthy, accepts the connection, and decodes nothing. This has already happened once here: UNIMPLEMENTED §7.8. ./scripts/connect-tracker.py --check inspects both sides of the mapping. traccar.org/port-check proves it from outside the network.
Hop 4Device known Traccar holds a device whose uniqueId is exactly the identifier the unit sends. The packet arrives and is thrown away: WARN Unknown device - 865282040015552, and no position is stored. With the allow-list on, a pattern that names only a prefix is refused with that same warning — it must match the whole identifier. --check reads back the registration state actually in force. --adopt-seen-id <id> creates the device under the identifier the server reported.
Hop 5Real position The unit has a fix, not merely a connection: sky view, and a valid A flag rather than V. An H02 HTBT keep-alive arrives on schedule while the map stays empty. A first fix from cold can take fifteen minutes — longer indoors or under a metal roof — so timing out early makes a working unit look broken. Dashboard: the A flag, and a plausible non-zero speed while moving. Antenna with a clear view of the sky.
Hop 6Read The dashboard reaches Traccar and the tachograph service on the loopback interface, and a person is signed in. An empty map on a stack whose API answers correctly. Traccar creates no users on a fresh install, so nobody can be signed in at all. ./scripts/smoke-test.sh
03

Bringing one up is one command

it does the four server-side steps and then waits

It checks the port mapping, reads back what this server will do with an unknown identifier, creates the device record so nobody drives Traccar's UI, prints the SMS block with your APN and server already substituted — and then waits, because only a stored position is proof. 

# server side only: is the H02 port really reaching Traccar?
./scripts/connect-tracker.py --check

# a new unit, from registration to a real position
./scripts/connect-tracker.py --imei 4210209006 --name AB123CD \
    --server vps.example.com --apn internet

It reports one of three states, and they are not the same thing:

Hop 4

registered

The device record exists. Nothing has talked to the server yet — the tracker, the SIM or the server address is still wrong.

Hop 5, partly

reached the server

Packets are arriving. There is no usable fix yet. Wait, move the tracker into the open, and check A versus V.

Hops 1–6

positioned

Real coordinates, through the real decoder, on the published port. This is the only state that means it works.

Two settings decide what happens at hop 4, and both live in .env:

  • TRACCAR_REGISTER_UNKNOWN=false (the default) — an unknown identifier is logged and ignored. Register the device first. This is the right setting for a production fleet on a public port.
  • TRACCAR_REGISTER_UNKNOWN=true — the device appears by itself, with TRACCAR_REGISTER_UNKNOWN_CATEGORY=truck so its speed and distance are not quietly wrong. Narrow it with TRACCAR_REGISTER_UNKNOWN_REGEX: 42102.*, not ^42102, which matches nothing.
04

Before it goes in a vehicle

the part that is not about the network
Power VCC to a constant, fused positive — not to ACC. The unit has no internal battery, so on ACC-only it is silent every night and loses its buffer on a power cut. ACC is an input signal for the ignition flag, never the supply.
Ground & antenna Chassis ground, cable short, routed away from the alternator and starter. Antenna with a clear view of the sky — that is worth more than any antenna upgrade.
Then bench-test Position moving when the tracker moves, ignition following the ACC switch, a sensible reporting interval, no repeated errors in docker compose logs -f traccar.
Two things on this hardware that stay disconnected, deliberately: the remote engine cut-off relay, and voice monitoring. Both are refused by design — see docs/ST-906L.md § Two capabilities you should refuse. An engine cut-off wired to an unverified unit is a moving-vehicle hazard, not a security feature.
05

What this sheet does not prove

stated, not implied

The listener, the decoder, the port mapping and the zero-touch path have all been exercised over real H02 traffic by scripts/simulate-fleet.py and connect-tracker.py. No physical unit has ever connected: the radio link, the SIM, GNSS reception and the ACC wiring are unverified, and docs/UNIMPLEMENTED.md is the register that says so. Order one tracker, walk this sheet, and only then buy more.
